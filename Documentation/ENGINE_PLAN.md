# CustomGameEngine project plan

The viewer switches among Cube, Oak, and Grove scenes with an outliner and linked Object, Mesh, Material, and Texture views. Oak and Grove share the FirstSettlers low-branched white oak LOD0 asset. The grove is the baseline for later LOD and GPU visibility work. Checkpoint 11 adds live reload for the mesh and shadow shaders through the Scene Inspector.

## Goals

Build a native engine for FirstSettlers and learn it one visible step at a time. Own the frame loop, rendering passes, asset-to-GPU path, and game-world behavior. Use focused libraries for tasks such as parsing asset files, physics, and navigation. Keep the current Unity project as a reference for art assets and gameplay behavior.

Use [Toni Macaroni’s forest showcase](https://www.youtube.com/watch?v=uR5EvBWxN14) as a visual reference. The first forest should have readable backlit leaves, crowns with convincing depth and gaps, believable ground contact, wind that feels coherent across a stand, and foliage that stays stable as the camera walks and turns. Judge close-up bark and leaves, a shaded forest edge, and a distant tree line separately.

Start on a flat plane. The longer-term world direction is authored terrain with optional offline, rule-based foliage scatter and hand placement. Large maps can stream authored regions as needed. Terrain modification, construction, tree harvesting, animation, physics, navigation, audio, and multiplayer should eventually be testable on small scenes. An authored baseline can still accept runtime edits.

## Proposed starting stack

| Area | Choice and reason |
| --- | --- |
| Engine and build | C++20, CMake, and the MSVC toolchain with a Windows SDK. This follows the native D3D12 examples and keeps Windows setup and future C++ library integration straightforward. Verify the installed toolchain when implementation begins. |
| Window and input | Win32 for the first viewer, matching Microsoft’s sample. Consider SDL3 when controller support, input needs, or another platform justify it. [D3D12 samples](https://github.com/microsoft/DirectX-Graphics-Samples/tree/master/Samples/Desktop/D3D12HelloWorld) · [SDL](https://github.com/libsdl-org/SDL) |
| Rendering | D3D12, HLSL, and DXC. Use a forward pass with indexed draws, a depth buffer, and a directional light. This gives us the draw path we’ll extend with instancing and compare against later GPU-driven paths. Revisit the API choice if another platform becomes a primary target. [DXC](https://github.com/microsoft/DirectXShaderCompiler) |
| Assets | Blender exports a glTF binary (`.glb`), and cgltf reads the file. The engine interprets the scene and uploads resources. Blender remains the first tool for mesh editing and scene placement. [Blender glTF exporter](https://docs.blender.org/manual/en/latest/addons/import_export/scene_gltf2.html) · [cgltf](https://github.com/jkuhlmann/cgltf) |
| Tools | D3D12 debug layer during bring-up, PIX for frame inspection and timing when needed, and Dear ImGui when a live control earns its place in the viewer. [PIX timing captures](https://devblogs.microsoft.com/pix/timing-captures/) · [Dear ImGui](https://github.com/ocornut/imgui) |

## The interface

- **Cube viewer.** A native window mostly occupied by the viewport. Launch with the sample `.glb` or pass a path to another asset. Left drag orbits around the sample, the wheel zooms, and `R` resets the view. Show the asset path and import error in a readable diagnostic if loading fails. The cube should sit on a plain ground plane under a fixed sun direction.
- **Foliage test scene.** Add a compact, collapsible panel with named camera views, sun angle, wind strength or pause, and tree count once we can draw a grove. Include a display for frame time and draw or visible instance counts as those measurements become available. Add a free-fly camera for moving through trees. Keep a known camera position and a repeatable camera route for comparisons.
- **Authoring tools.** Add object selection and transform controls when we need to adjust placement without returning to Blender. Add a scene save format once the viewer is used to make edits we need to keep.

## First build and learning checkpoints

1. **Clear and present.** Confirm the compiler, SDK, CMake, and GPU device. Open a Win32 window, clear it to a known color, and present.
2. **Draw a triangle.** Upload three colored vertices, compile the vertex and pixel shaders with DXC, and issue a draw after clearing the back buffer. This gives us a working reference for vertex input, rasterization, and pixel shading.
3. **Load and inspect a real Blender asset.** Export a cube with an obvious node offset or rotation so the test detects an ignored transform. Read positions, normals, indices, and the node transform. Upload vertex and index buffers, apply the camera transforms, depth-test, and shade the visible faces. Draw a ground plane, wire up orbit, zoom, and reset, and check scale and orientation from multiple angles. Test a missing file and verify the documented build and launch commands from a clean build. Explain how the GLB reaches the screen and capture a screenshot if the graphics environment permits. [glTF 2.0 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)
4. **Compare 4× MSAA with single-sample rendering.** Query device support for the color and depth formats, use matching sample counts in the attachments and pipeline state, and resolve multisampled color into the single-sample swap chain. Keep `M` as a live toggle so the same camera view can expose the difference along slanted geometry edges. [D3D12 sample quality levels](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_multisample_quality_levels) · [D3D12 resolve](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-resolvesubresource)
5. **Import one oak.** Export the FirstSettlers low-branched white oak LOD0 from its Blender source. Preserve its UVs, transforms, and bark and foliage assignments. Use flat debug tints and frame the whole tree at its original scale so we can inspect the trunk and crown before adding textures.
6. **Make the canopy readable.** Sample the bark and crown base-color maps using their authored UVs, discard foliage pixels below the material's alpha cutoff, and preserve alpha coverage across mip levels. Add a small backlighting term for double-sided leaf cards.
7. **Cast a sun shadow.** Fit a fixed orthographic light view to the test scene. Draw caster depth using the same leaf cutout, then sample the shadow map in the camera pass. Check that the trunk connects to its shadow and the crown lets light through.
8. **Add wind.** Bend the bark and foliage together using a shared height-weighted offset in both vertex shaders. Keep the trunk base fixed and pad the shadow view for the full sway. Use `P` to pause the wind at its current pose and resume from that pose.
9. **Draw a grove.** Reuse the oak's geometry and textures in both passes with indexed instancing. Compare 1, 25, 100, and 400 trees on a repeatable camera route. Show FPS, CPU submission time, and GPU frame time in a compact viewport HUD.

Use `CMakeLists.txt`, `src/`, `shaders/`, `assets/`, and a short `README.md` when coding starts. Keep the window and frame loop, GLB loading, rendering and GPU resource lifetime, and camera input easy to find. The loader hands the renderer mesh data and an object transform. The viewer supplies the camera and light for the current frame. Add new modules as their responsibilities appear in the working viewer.

## Rendering-first checkpoints

Cube, Oak, and Grove become named scenes in checkpoint 10. Each has object placements, a sun and environment, and named camera views. Cube remains a rendering sanity check, Oak is the close-up material and geometry comparison, and Grove is the repeatable performance scene. Add a separate Forest Edge scene once we need terrain, grass, and longer sightlines. The existing GLB launch option can open an inspection scene around an arbitrary asset.

### Scene and inspector design

| Area | What it owns or shows |
| --- | --- |
| **Scene and outliner** | The scene owns named object instances with stable IDs, transforms, and asset references, plus lighting and camera presets. The outliner starts with a short list. Show the generated grove as a group with a count and a way to inspect one representative tree. The renderer batches those placements for drawing. |
| **Object inspector** | Show the selected object's transform, mesh reference, and material slots. Selecting one tree identifies one placement. Follow its references to see what the grove shares. |
| **Mesh inspector** | Show source, bounds, vertex and triangle counts, primitives, UV sets, and assigned material slots. Add active LOD, cluster counts, and bounds overlays as those features arrive. |
| **Material inspector** | Show editable preview values for base-color factor, alpha cutoff, and leaf backlighting, with links to the bound textures. Label shared asset changes clearly. Editing the shared leaf material updates every tree that uses it. An instance override can follow when a scene needs one. |
| **Texture inspector** | Start with a thumbnail, dimensions, color space, and mip count. Add RGB/alpha and mip previews for the crown atlas when diagnosing foliage coverage. Reuse the referenced texture across materials where its sampling and processing requirements agree. |
| **Scene controls** | Keep sun, wind, camera presets, tree count, and MSAA in a collapsible panel. Preserve the small top-right performance HUD. Put pass timings and debug overlays in the panel as they become useful. |

Start with built-in scene definitions and transient preview edits. Add a small scene file once we want to keep authored placements and settings between runs. Blender remains the mesh and texture authoring tool. Start selection in the outliner. Viewport picking and transform gizmos can follow when arranging Forest Edge needs them.

The viewer owns input, camera controls, selection, and scene switching. The scene holds placements and settings. Asset loading produces shared mesh, material, and texture data from GLBs. D3D12 owns GPU resources, pipelines, and draw batches. Move the current startup scene setup out of the application loop as we introduce these boundaries. Keep the existing camera and shadow passes traceable, and extract each new rendering pass when it has its own resources or inputs. Stable scene and asset references should survive rebuilding GPU resources or changing how a tree is rendered.

### Checkpoints and verification

| Checkpoint | What we build | What we verify |
| --- | --- | --- |
| **10. Scenes and inspector** | Add Cube, Oak, and Grove scene definitions and an in-app selector. Use Dear ImGui for the outliner, scene controls, and one context-sensitive inspector with linked Object, Mesh, Material, and Texture views. Start with asset metadata and a few editable material values. | Switch scenes in one session. Inspect one oak and follow its bark and leaf slots to the correct textures. Confirm the grove shares those assets, the sun updates both shading and shadows, and the panel's input stays separate from camera input. [Dear ImGui Win32/D3D12 example](https://github.com/ocornut/imgui/tree/master/examples/example_win32_directx12) |
| **11. Live shader reload** | Run DXC from a reload action, display diagnostics in the panel, and build all affected camera, shadow, and MSAA pipelines before swapping. Keep scene, camera, and preview values during the reload. | Change leaf backlighting live. Break HLSL and confirm the previous pipelines keep drawing. Fix it and verify both camera and shadow paths reload in both MSAA modes. [DirectX Shader Compiler](https://github.com/microsoft/DirectXShaderCompiler) |
| **12. Make one oak look right** | Compare the existing oak against its FirstSettlers source. Test the packed bark normal and crown surface maps after checking their channel layout. Improve sky fill, leaf transmission, and shadow filtering. Add fixed close-up, underneath, and backlit views with material debug modes. | Compare bark relief, leaf edges, the shaded crown interior, and backlit gaps at fixed exposure. Move slowly around the crown and check for shimmer and shadow artifacts. Record which changes actually improve the oak. |
| **13. Build a forest-edge render scene** | Add authored terrain, grass, an open path, sky, and distance haze. Use a free-fly camera and a repeatable ground-height route. Save scene settings when they need to be shared or reproduced. | View ground contact from standing height, move between open sun and canopy shade, and inspect grass and tree silhouettes in motion. Keep the flat grove route available for controlled comparisons. |
| **14. Establish the distance baseline** | Add per-pass GPU timings, submitted and visible counts, and one conventional whole-tree LOD. Add CPU frustum culling as a reference for GPU visibility. Keep the existing all-LOD0 mode and separate camera and light visibility. | Compare median and slow frames, triangle counts, and canopy coverage at fixed resolution and exposure. Check for popping and make sure off-camera trees can still cast visible shadows. |
| **15. Build and inspect triangle clusters** | Use meshoptimizer as a starting point for offline cluster building. Use the 4,192-triangle oak as the control and the existing detailed low-branched oak source as a candidate for a geometry-rich test asset. Start with one representative branch if the full source makes iteration slow. Draw colored cluster IDs and bounds through the indexed renderer. | Confirm clustered full-detail drawing matches the source's geometry, material slots, and silhouette. Check that cluster bounds enclose the geometry under wind. Record asset size, cluster count, and bake time. [meshoptimizer cluster LOD builder](https://github.com/zeux/meshoptimizer/blob/master/demo/clusterlod.h) |
| **16. Select clustered LOD by screen-space error** | Bake a simplification hierarchy and select a valid set of clusters according to projected error. Start with CPU selection and a debug overlay. Preserve shared boundaries at mixed detail levels. | Move across a single oak and confirm that a near branch can stay detailed while the farther crown simplifies. Inspect seams, missing triangles, overlap, and transitions. Compare against the whole-tree LOD at similar GPU cost and record the image differences. |
| **17. Prototype a voxel crown** | Bake one crown region into sparse 3D cells with coverage, color, and normal information. Account for the alpha mask if the source uses cards, or voxelize explicit leaves. Render a few fixed voxel sizes under the same sun. Keep trunk and major branches as triangles. | Orbit and relight the same crown. Compare silhouette, thickness, gaps, parallax, and memory against triangles. Check that the crown neither fills in nor vanishes as cells get coarser. An existing impostor can serve as another comparison if it is practical to import. [Epic Nanite Foliage](https://dev.epicgames.com/documentation/unreal-engine/nanite-foliage) |
| **18. Integrate triangle-to-voxel transitions** | Add voxel representations to eligible hierarchy regions and switch by projected error. Add a forced mode for each representation, plus debug views of the transition. Keep foliage geometry voxels separate from any future indirect-lighting field. | Travel toward and away from the crown at fixed exposure. Check transition stability, gaps, wind, and shadow agreement. Compare GPU time and resident memory with the triangle-only hierarchy and whole-tree LOD. |
| **19. Move selection and drawing onto the GPU** | Use compute to cull and compact instances or clusters, then submit through D3D12 indirect draws. Reuse the CPU selection as a reference. Evaluate mesh shaders with the same cluster data once the indirect path has measurements. | Compare visible sets and images against CPU selection. Measure the combined cost of culling, drawing, and shadows. Check supported hardware and keep a working indexed path. [D3D12 indirect drawing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/indirect-drawing) · [D3D12 mesh shaders](https://microsoft.github.io/DirectX-Specs/d3d/MeshShader.html) |

The cluster and voxel checkpoints are experiments with explicit comparisons. Cluster partitioning alone is not clustered LOD. The hierarchy, its error metric, and mixed-detail selection are what make it possible to simplify different parts of one tree independently. A successful voxel crown preserves the view through the foliage and earns its cost on the same route. Epic's implementation gives us a reference for geometry-to-voxel transitions, and we can choose our own cell payload and renderer.

After the first voxel comparison, prioritize what the scenes reveal. If motion makes foliage shimmer, test alpha coverage and temporal stability on the ground-height route. If sunlight and shade lack depth, use the forest edge or a simple roof-and-doorway fixture to test indirect light. If distant stands dominate cost, consider region proxies and streaming once the grove gives us evidence.

The panel provides immediate value changes. DXC reload handles shader source changes inside the viewer. Native C++ uses the normal build. Gameplay script reload becomes a separate experiment once there is behavior and state to edit. Keep physics, construction, terrain edits, animation, audio, navigation, and multiplayer in the later engine plan.


For grove comparisons, record the GPU, build, resolution, camera route, and rendering settings. Start with frame time in milliseconds and draw or instance counts. Add CPU and GPU timings as needed, including culling, shadows, and drawing. Compare typical and slow frames over the same warmed-up route. Use a short moving capture to judge foliage shimmer and LOD transitions.

### Research behind the later experiments

- The earlier FirstSettlers source audit attributes GPU-driven meshlets, hardware mesh shaders, clustered LOD, voxel foliage at distance, far proxies that omit individual instance data, and hybrid screen-space/voxel indirect lighting to Toni’s showcase. It also records practical art and rendering choices such as tree-size and canopy variation at forest edges, and contact shadows for small grass. The engine’s API, cluster builder details, voxel payload, and occlusion algorithm remain open. Creator posts are linked here from that audit. [Showcase](https://www.youtube.com/watch?v=uR5EvBWxN14) · [Meshlets and voxels](https://x.com/ToniMacaroniy/status/2113574482107646296) · [Mesh shaders](https://x.com/ToniMacaroniy/status/2113395585399337153) · [Scatter](https://x.com/ToniMacaroniy/status/2117374994715938925) · [Grass shadows](https://x.com/ToniMacaroniy/status/2116137664923705681)
- Epic’s experimental Nanite Foliage is a technical reference for preserving crown coverage when leaves become too small to resolve. Its builder can switch a cluster from triangles to voxel bricks based on simplification error. Epic also describes storing a distribution of surface normals for shading. Our first voxel experiment can start with approximate leaf coverage and orientation from one crown and test whether it holds up at distance under changing sun. Crown voxels represent geometry. A future indirect-lighting field would carry lighting and visibility data. [Epic’s Nanite Foliage documentation](https://dev.epicgames.com/documentation/unreal-engine/nanite-foliage)

## How the rest of FirstSettlers fits

| System | First useful test or decision |
| --- | --- |
| Physics and player control | A character walks around the plane, a trunk collider, and one building piece. Evaluate Jolt when we need character collision and rigid bodies. [Jolt Physics](https://github.com/jrouwe/JoltPhysics) |
| Building and terrain modification | Place one snapped piece and make one terrain edit in a test yard. Track logical world state independently of render instances. Give harvestable trees and placed objects stable identities when edits need to persist. Update affected rendering, collision, and navigation data from the same world edit. |
| Animation | Import a single character rig and one clip. Verify skinning and playback before designing animation state and blending. |
| Navigation | Route an agent around the building piece, then change the obstruction and update the affected navigation area. Evaluate Recast/Detour once there’s traversable terrain to test. [Recast/Detour](https://github.com/recastnavigation/recastnavigation) |
| Audio | Play a positional footstep and a grove ambience loop. Choose a library when positional audio is ready to test. |
| Multiplayer and saves | Once local world edits work, test two players placing or harvesting an object with an authoritative host. Store authored world data and persistent edits in terms of stable objects and regions so the same state can be saved or synchronized. Transport and save format are open. |
